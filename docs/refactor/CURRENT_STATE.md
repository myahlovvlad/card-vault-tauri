## 3. Existing functionality (as implemented today)

- Photograph/upload multiple photos per received business card, tag each as front/back/other.
- OCR (Tesseract.js, `rus+eng`, LSTM engine) runs automatically after photo upload and can be re-run manually.
- A regex/heuristic parser (`parseBusinessCardText` in `lib/ocr.ts`) extracts a *single* guess each for full name, company, job title, phone, email, website from the raw OCR text — no confidence scores, no bounding boxes, no multiple candidates, no per-token classification.
- User reviews/edits the OCR-filled form before saving (never auto-saves without confirmation).
- Folders: create, delete (contacts move to "Без категории" on folder delete), assign a card to one folder.
- Starring ("important") with priority sort (starred first, then by `updatedAt`).
- Full-text search across name/company/jobTitle/phone/email/website/comment/raw OCR text — plain substring match, not FTS.
- JSON backup/restore (whole `AppData` object, photos inlined as data URLs).
- CSV export of the contact list.
- Single-card `.vcf` (vCard 3.0) export/download.
- "My Cards": create own card(s) (no photo/OCR, just a form), shown as a swipeable fanned stack, full-screen present mode with a flip animation between a vCard-encoded QR and the card details, Web Share API / `.vcf` download / clipboard copy.
- QR scanner: `getUserMedia` + `jsQR` polling loop, decodes a vCard (or arbitrary text) from camera or manual paste, and hands it to the same received-card confirm-before-save editor used for OCR.
- Responsive layout: sidebar collapses to a slide-over on narrow viewports; grid becomes 1-column.

## 4. Storage (today)

- **IndexedDB only**, via `idb-keyval`, one key (`card-vault-data-v1`) holding the entire `AppData` object as a single JSON blob.
- Photos are stored as **base64 data URLs inside that same JSON blob** (compressed client-side: max edge 1800px, JPEG quality 0.84, via `<canvas>`).
- No SQLite, no filesystem blob storage, no Tauri SQL/FS plugin usage anywhere.
- Schema versioning exists at the JSON level only: `schemaVersion: 1 → 2` migration (`migrate()` in `storage.ts`) added `ownCards: []` when the "My Cards" feature shipped. This is the *only* precedent for data migration in the codebase, and it is in-memory/synchronous, not transactional.
- No content-addressing, no thumbnails, no per-photo metadata (width/height/mime/sha256) — a photo is just `{ id, dataUrl, fileName, side }`.

## 5. Domain model (today) — `src/types.ts`

```ts
type CardPhotoSide = 'front' | 'back' | 'other';
interface CardPhoto { id; dataUrl; fileName; side; }
interface BusinessCard {
  id; folderId; fullName; company; jobTitle;
  phone; email; website;              // single string each, not arrays
  comment; starred; photos: CardPhoto[]; ocrText;
  createdAt; updatedAt;
}
interface Folder { id; name; createdAt; }
interface AppData { schemaVersion: 2; folders: Folder[]; cards: BusinessCard[]; ownCards: BusinessCard[]; settings: { ocrLanguage } }
interface CardDraft { /* BusinessCard fields minus id/timestamps */ }
```

Gaps vs. the target §6 domain model in the refactor spec: no `Contact`/`BusinessCard` split (physical source vs. person), phone/email/website are single strings not arrays, no `Tag`/`ContactTag`, no `OcrRun`/`OcrBlock`/`FieldCandidate`/`UnclassifiedText`, no `SyncOperation`/`SyncCursor`/`AuditEvent`, no `Workspace`/`WorkspaceMember`, no soft-delete (`deleted_at`)/`revision`/`device_id` fields anywhere.

## 6. OCR (today)

- `src/lib/ocr.ts`: `recognizeImages()` dynamically imports `tesseract.js`, creates one worker per call (`createWorker(languages, OEM.LSTM_ONLY, ...)`), recognizes each image sequentially, joins raw text, and runs it through `parseBusinessCardText()`.
- **Not bundled offline**: Tesseract.js fetches its worker script, WASM core, and `rus.traineddata`/`eng.traineddata` from Tesseract.js's default CDN on first use (this is explicitly called out as a known limitation in `README.md`: "для первой OCR-сессии обычно требуется доступ к интернету"). This directly conflicts with refactor spec §10 ("первое распознавание после чистой установки должно работать без интернет-соединения").
- No `OcrProvider` interface, no `OcrDocument` (blocks/lines/tokens/bounding boxes/confidence/language), no golden corpus, no platform-native OCR acceleration path.
- Classification (`parseBusinessCardText`) is a single deterministic pass (email/phone/website regex, then a job-title keyword list, then positional heuristics for name/company) — no layered pipeline, no `FieldCandidate` objects, no confidence scores, no `UnclassifiedText` retention (unmatched lines are simply dropped).

## 10. Known limitations of the current implementation (self-documented in `README.md`)

Quoting the app's own "Ограничения MVP" section, translated:
- OCR field assignment is heuristic and not guaranteed correct (why user confirmation exists).
- No cloud multi-user sync, no owner/reviewer permission roles.
- No CRM/calendar OAuth (the `ContactConnector` interface exists but `PlaceholderCrmConnector` always returns `ok: false`).
- iOS only buildable on macOS/Xcode.
- Android/iOS require standard Tauri mobile target initialization on the dev machine.
- HEIC photo support depends on the OS WebView decoder.
- The QR scanner uses `getUserMedia`, not a native Tauri camera plugin — without camera permission granted at the OS level, only manual text entry works.

## 11. Delta vs. this refactor specification — summary of what Phase 0 confirms is *not* yet true

This is expected — it is the reason the refactor exists. This document is the reference point Phase 1+ diffs against.
